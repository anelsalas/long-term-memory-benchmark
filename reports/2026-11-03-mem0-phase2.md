# Mem0 phase 2: ten LongMemEval-S questions

GPT judged Mem0 correct on 9/10, dense vector search on 6/10, and the same reader with labelled evidence on 10/10. This selected ten-question pilot is too small to establish general superiority.

## Terms

- **LongMemEval_S.** A public benchmark of long chat histories. Each question
  comes with about 50 earlier chat sessions (~115k tokens), and the answer is
  hidden somewhere in them.
- **Session.** One earlier conversation in a question's history.
- **Multi-session question.** A question whose answer needs facts from two or
  more sessions, for example adding up things mentioned on different days.
- **Abstention question** (ID ending in `_abs`). The history does not contain
  the answer; the correct reply is to say so.
- **Reader.** The model that reads the supplied context and answers the
  question. Here, GPT-6.1-sol at high effort.
- **Judge.** A model that compares the reader's answer with the benchmark's
  reference answer and says correct or not, using the official LongMemEval
  judge prompts. Here, also GPT-6.1-sol at high effort.
- **Context budget.** The reader is never given the whole history. Each method
  picks up to about 6,000 tokens of it (estimated as UTF-8 bytes / 4) to show
  the reader.
- **Token.** The unit models count text in; roughly three quarters of an
  English word.
- **Dense search (dense vector search, dense embeddings).** The baseline. Every
  message in the history is turned into a vector of numbers (an "embedding",
  here by the local Qwen3-Embedding-0.6B model) that captures its meaning. The
  question is embedded the same way, and the messages whose vectors are closest
  to it are packed into the budget. "Dense" refers to these vectors, as opposed
  to keyword search (BM25).
- **Mem0.** An open-source memory system. Before any question is asked, it
  reads each session with a language model and writes short facts ("memories"),
  for example "User moved to Denver in March 2023". At question time it
  searches those memories, not the raw messages.
- **Ingestion.** Mem0's up-front step of reading every session and writing
  memories. Here it ran GPT-6.1-sol at low effort, one call per session. It is a
  one-time cost per history, paid before answering.
- **Memory events.** Memories Mem0 added or changed during ingestion.
- **Labelled evidence (control).** The benchmark marks which sessions and
  messages contain the answer. Giving the reader only those messages shows how
  well it does with perfect retrieval: an upper bound for any memory method.
- **Labelled sessions / all represented.** How many sessions are marked as
  evidence for the question, and whether every one of them appears in the
  source information of the memories Mem0 selected.
- **True / False.** The judge's verdict: correct or not correct.
- **Sign test, p = 0.25.** A check of whether the wins could be luck. Mem0 won
  3 questions and lost none. A fair coin gives 3 heads or 3 tails out of 3
  tosses 25% of the time, so this sample is too small to call the difference
  real.
- **CLI framing.** Extra instructions the Codex command-line tool adds to every
  call (about 5,000 tokens), which a direct API call would not include.

## Results

The dense and labelled-evidence results are reused from the November 2 run;
they were not rerun alongside Mem0. Run-to-run variance is unmeasured. Mem0
won three paired questions, lost none and tied seven; the two-sided sign-test
result is p = 0.25. Ten questions cannot separate the two methods reliably.

Mem0 ingestion used 490 model calls, 7,712,359 input tokens and 394,401 output tokens. The preliminary input projection was 7.4 million. Summed session client time was 29,385 seconds (about 8 hours 10 minutes), excluding gaps. The bridge recorded 512 attempts including all answer, judge and superseded-pilot calls, below the 1,500 cap. Actual monetary cost was not measured.

Ingestion averaged about 15.7k input tokens per call, or 771k per question,
compared with about 11k reader input tokens per question. An estimated 5k tokens
per call, roughly 2.4 million in total, is Codex CLI framing; a direct API
deployment could avoid that CLI-specific overhead. This is an estimate, not a
measured decomposition of each request.

The Mem0 and dense readers received the same estimated 6,000-token content budget. Across the ten cases, Mem0 reader input was 109,443 tokens and dense reader input was 108,007. Mem0 ingestion is a separate upfront cost; the methods selected different content and their retrieval timing paths differed.

Evidence presence means all labelled evidence session identifiers appeared in selected memory metadata. It does not verify the original evidence turns. GPT served as both answer model and judge, and the histories are public benchmark data. The first pilot was selected before the remaining cases; the small sample and model grading limit the conclusions. The local resource sample covers only part of the initial ingestion and does not measure remote inference.

The abstention case `6456829e_abs` has two labelled session IDs in the pinned
dataset. Their presence in memory metadata records provenance of those sessions;
it does not mean the absent answer exists in them. All ten cases have at least
one labelled session, so none requires an evidence-presence value of not applicable.
